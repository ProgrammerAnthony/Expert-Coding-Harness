# 深化（Deepening）

如何在给定依赖的情况下，安全地将一组浅模块深化。使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**。

## 依赖分类

评估深化候选项时，先对其依赖进行分类。分类决定了深化后的模块如何跨接缝进行测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。**始终可深化**——合并模块，直接通过新接口测试。无需适配器。

### 2. 本地可替代（Local-substitutable）

拥有本地测试替代品的依赖（如 PGLite 替代 Postgres、内存文件系统）。若替代品存在则可深化。深化后的模块在测试套件中使用替代品运行。接缝在模块内部，模块外部接口处无端口。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义**端口**（接口）。深模块拥有逻辑；传输层以**适配器**形式注入。测试使用内存适配器，生产使用 HTTP/gRPC/队列适配器。

建议形式：*"在接缝处定义端口，为生产实现 HTTP 适配器，为测试实现内存适配器，使逻辑集中在一个深模块中，即便它跨网络部署。"*

### 4. 真正外部（Mock）

不受控的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入端口；测试提供 Mock 适配器。

## 接缝纪律

- **一个适配器意味着假设性接缝，两个适配器才意味着真实接缝。** 除非至少两个适配器合理（通常是生产 + 测试），否则不引入端口。单适配器接缝只是多余的间接层。
- **内部接缝 vs 外部接缝。** 深模块可以有内部接缝（对实现私有，供自身测试使用）和外部接缝（在接口处）。不要仅因为测试使用内部接缝就将其暴露在接口上。

## 测试策略：替换，而非叠加

- 一旦在深化后的模块接口处有了新测试，原浅模块上的旧单元测试就成了废代码——删掉它们。
- 在深化后的模块接口处编写新测试。**接口是测试表面。**
- 测试通过接口断言可观测的结果，而非内部状态。
- 测试应能在内部重构后继续通过——它们描述行为，不描述实现。若实现变更导致测试失败，说明测试测的是接口之后的东西，而非接口本身。
