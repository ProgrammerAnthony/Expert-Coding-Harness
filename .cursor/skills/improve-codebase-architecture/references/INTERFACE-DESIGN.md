# 接口设计（Interface Design）

当用户想为已选定的深化候选项探索多种接口方案时，使用本并行子代理模式。基于 Ousterhout 的"设计两次（Design It Twice）"——你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**。

## 流程

### 1. 框定问题空间

在派发子代理之前，为选定候选项撰写一份面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它依赖的内容，以及这些依赖属于哪个分类（见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的说明性代码草图，用以具体化约束——不是方案，只是让约束变得具体

将这份说明展示给用户，然后立即推进到第 2 步。用户阅读和思考的同时，子代理并行工作。

### 2. 派发子代理

使用 Agent 工具并行派发 3 个以上子代理。每个子代理都必须为深化后的模块产出**显著不同**的接口设计。

给每个子代理提供独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖分类、接缝后面是什么）。该简报独立于第 1 步中面向用户的问题空间说明。给每个代理分配不同的设计约束：

- **代理 1**："最小化接口——最多 1-3 个入口点。每个入口点最大化杠杆。"
- **代理 2**："最大化灵活性——支持多种使用场景和扩展。"
- **代理 3**："为最常见的调用方优化——让默认场景变得极简。"
- **代理 4**（如适用）："围绕端口与适配器设计，处理跨接缝依赖。"

在简报中同时包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，使每个子代理的命名与架构语言和项目领域语言保持一致。

每个子代理输出：

1. 接口（类型、方法、参数——以及不变量、顺序约束、错误模式）
2. 展示调用方如何使用的示例代码
3. 接口背后的实现隐藏了什么
4. 依赖策略与适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆高的地方和薄弱的地方

### 3. 呈现并对比

依次呈现各设计，让用户能逐一吸收，然后用散文对比它们。从**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**三个维度进行对比。

对比之后，给出你自己的推荐：你认为哪个设计最强以及原因。若不同设计中的元素组合会更好，提出混合方案。要有主见——用户需要的是强有力的判断，而不是菜单。
