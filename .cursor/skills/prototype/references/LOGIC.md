# 逻辑原型（Logic Prototype）

用于**业务逻辑、状态转换或数据结构**问题的微型终端交互 App——那些在纸上看起来合理、但实际推演时才会暴露问题的东西。

## 适用场景

- "我不确定这个状态机能不能处理先 X 后 Y 的边界 Case。"
- "这个数据模型能否表示某某特殊情况……"
- "我想在写代码前先感受一下 API 应该长什么样。"
- 任何需要**按键并观察状态变化**的问题。

如果问题是"界面应该长什么样"——分支选错了，请用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

写代码前，写下你在原型化的状态模型和问题。一段话，放在原型的 README 或文件顶部注释里。选错问题的逻辑原型是纯浪费——明确问题以便后续核查。

### 2. 选语言

使用宿主项目已有的语言。若项目没有明显的 runtime（例如纯文档仓库），询问用户。

### 3. 将逻辑隔离在可移植模块中

把真正回答问题的逻辑放在一个小型纯接口后面，以便后续提取进真实代码库。正确形态取决于问题：

- **纯 reducer** — `(state, action) => state`。适合动作是离散事件、状态是单值的场景。
- **状态机** — 明确的状态和转换。适合"当前哪些动作合法"本身就是问题的一部分时。
- **一组纯函数**作用于简单数据类型。适合没有隐式当前状态，只有变换时。
- **带清晰方法面的类/模块**，当逻辑本身需要维护内部持续状态时。

保持纯粹：无 I/O、无终端代码、无用于控制流的 `console.log`。TUI 导入并调用它；不反向依赖。

### 4. 构建最小 TUI 暴露状态

**轻量 TUI**——每次 tick 清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价物）并重新渲染整帧。用户始终看到一个稳定的视图。

每帧两个部分（顺序固定）：

1. **当前状态**，格式化输出（每字段一行，或 JSON）。对字段名/章节标题使用**粗体**，对次要上下文（时间戳、ID、派生值）使用_淡色_。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 推进时钟  [q] 退出`。

行为：
1. **初始化状态**——单个内存对象/结构体。启动时渲染第一帧。
2. **逐键读取**，派发到更新状态的处理函数。
3. **每次操作后重新渲染**完整帧——不追加，替换。
4. **循环直到退出。**

整帧应能在一个屏幕内显示。

### 5. 一条命令运行

在项目现有任务管理器中添加脚本（`package.json scripts`、`Makefile`、`justfile`、`pyproject.toml`）。用户应能运行 `pnpm run <prototype-name>` 或等价物，不需要记路径。

### 6. 交给用户

给出运行命令。有趣的时刻通常是用户说"等等，这不应该是可能的"或"哦，我以为 X 会不同"——这些是**想法层面的 Bug**，这正是原型的意义。

### 7. 记录答案

原型完成任务后，答案是唯一值得保留的东西。将其记录在持久化位置（commit message、ADR、issue，或原型旁边的 `NOTES.md`）。

## 反模式

- **不要写测试。** 需要测试的原型已不再是原型。
- **不要连接真实数据库。** 使用内存存储，除非问题本身明确涉及持久化。
- **不要泛化。** 不做"万一以后需要支持 X"的预留。原型回答一个问题。
- **不要将逻辑和 TUI 混在一起。** 若 reducer/状态机引用了 `console.log`、prompt 或终端转义码，它就不再可移植了。
- **不要将 TUI Shell 带入生产。** Shell 是为手动终端操作优化的；逻辑模块才是值得保留的部分。
