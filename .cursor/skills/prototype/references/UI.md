# UI 原型（UI Prototype）

在单个路由上生成**几个差异显著的 UI 变体**，通过浮动底栏切换。用户在浏览器中翻看变体，选出心仪的（或取各家之长），然后删除其余部分。

如果问题是关于逻辑/状态而非界面外观——分支选错了，请用 [LOGIC.md](LOGIC.md)。

## 适用场景

- "这个页面应该长什么样？"
- "我想在决定前看几个仪表盘选项。"
- "试几个不同的设置页面布局。"
- 任何用户否则会在脑中反复比较三个模糊方案的情况。

## 两种子形态——强烈优先选 A

UI 原型在**贴近真实 App 其余部分**时更易判断——真实 header、真实 sidebar、真实数据、真实密度。孤立路由是真空：每个变体单独看都不错。**默认选子形态 A**。只有当原型确实没有合适的宿主页面时才用 B。

### 子形态 A — 调整已有页面（优先）

路由已存在。变体**渲染在同一路由上**，通过 `?variant=` URL 搜索参数切换。现有数据获取、params、auth 保持不变——只有渲染部分随变体切换。

若原型针对的是尚不存在但**自然上属于某页面**的内容（仪表盘新区块、设置页新卡片、已有流程新步骤）——仍属于子形态 A，将变体挂在宿主页面内。

### 子形态 B — 新页面（最后手段）

仅当被原型化的内容确实没有可嵌入的已有页面时使用。

按项目现有路由规范创建**一次性路由**——命名中包含 `prototype`（如路径或文件名中含此词）。相同的 `?variant=` 模式。

确定选子形态 B 前，再检查一遍：真的没有现有页面可以嵌入吗？

## 流程

### 1. 明确问题并选 N

默认生成 **3 个变体**。超过 5 个会失去"显著差异"，变成噪声。

用一行话写下计划（放在原型所在位置或文件头注释）：

> "三个设置页变体，通过 `?variant=` 切换，挂在已有 `/settings` 路由上。"

### 2. 生成显著差异的变体

起草每个变体，遵守：

- 页面用途和可访问数据。
- 项目组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
- 清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**——不同布局、不同信息层级、不同主要操作，不只是不同颜色。三个略有调整的卡片网格不是 UI 原型，那是壁纸。若两个草案太相似，给其中一个加约束"禁止使用卡片网格"再重来。

### 3. 串联变体

在路由上创建单个切换器组件：

```tsx
// 伪代码——按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

**子形态 A**：保留切换器上方所有现有数据获取；只有渲染的子树随变体切换。  
**子形态 B**：一次性路由挂载同样的切换器。

### 4. 构建浮动切换栏

屏幕底部居中的小型固定定位栏，三部分：

- **左箭头** — 切换到上一个变体（循环）。
- **变体标签** — 显示当前变体 key，以及变体导出的名称（如有），例如 `B — 侧边栏布局`。
- **右箭头** — 向前切换（循环）。

行为：
- 点击箭头通过框架 router 更新 URL 搜索参数（Next.js `router.replace`、React Router `navigate` 等），使变体可分享且刷新稳定。
- 键盘：`←` `→` 方向键也可切换。`<input>`、`<textarea>`、`[contenteditable]` 获得焦点时不拦截方向键。
- 视觉上与页面有明显区别（高对比度胶囊、细微阴影），使其明显不属于被评估的设计。
- **生产构建中隐藏**——通过 `process.env.NODE_ENV !== 'production'` 或等价检查控制，防止误合并后上线。

将切换器放在单个共享组件中，两种子形态复用。

### 5. 交给用户

给出 URL（及 `?variant=` 的各 key）。用户随时翻看。有趣的反馈通常是**"我想要 B 的 header 配 C 的 sidebar"**——那才是他们真正想要的设计。

### 6. 记录答案并清理

确定胜出变体后，写下是哪个以及原因（commit message、ADR、issue，或原型旁边的 `NOTES.md`）。然后：

- **子形态 A** — 删除失败变体和切换器；将胜出者折叠进已有页面。
- **子形态 B** — 将胜出变体提升为真实路由，删除一次性路由和切换器。

不要遗留变体组件或切换器。它们腐烂得很快，会混淆下一个读者。

## 反模式

- **变体只在颜色或文案上有差异。** 那是调整，不是原型。真正的变体在结构上有分歧。
- **变体之间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就失去意义了。每个变体都应能自由推翻布局。
- **将变体连接到真实写入操作。** 只读原型完全够用。若变体需要写入，指向一个 stub——问题是"界面该长什么样"，不是"后端能不能用"。
- **直接将原型提升到生产。** 变体代码是在原型约束下写的（无测试、错误处理极简）。折叠进真实代码时请重新认真编写。
